# Source restart and viewer updates, 2026-09-28

The user reported that the display froze or disappeared when restarting the test
PC, then that Ctrl-Alt-Del produced a beep and keyboard initialization while the
old red BIOS image remained visible. The test host itself retained its ten-day uptime,
Linux 7.2.5 kernel, and initialized original VGA2USB at USB path 1-12.2.

The initial capture log ended after a 612768/614304-byte frame; its native process
was still waiting in USB event handling. The ffplay process also remained alive,
although another window was in front. Stopping only this session's reader allowed
a valid B1 response again: `6f 7d 01 c2 00 f9 0a bf 02 00`. A fresh complete
snapshot showed a recognized 101/102-key keyboard. No host or USB device reset,
EEPROM write, kernel module, or firmware re-upload was needed.

## Repair and offline checks

Pending bulk reads now share an indefinite poll loop with a Linux timerfd that
wakes every 100 ms to observe documented B1 status. An observed absent, changed,
or incomplete status cancels and drains pending reads before their buffers are
freed. A short frame also queries current status before phase-recovery retries.
There is no elapsed frame or process deadline. USB transfer timeout arguments
remain zero; the libusb callback dispatcher is nonblocking after poll readiness.

Continuous mode emits one generated black frame on source loss/unavailability,
keeps its pipe open, and waits for supported timing. The clear frame preserves the
selected/last source dimensions. One-shot captures still fail without publishing
incomplete pixels. A transient zero-byte B1 response was observed during pipeline
restart, followed by a valid independent status read; continuous mode now retries
nonnegative incomplete status replies. Negative USB errors remain fatal.

ASan/UBSan checks cover pending-read loss, restored signal and resumed red pixels,
PPM boundaries, one-shot pending loss, absent signal at startup, 640×480 clear
geometry, short-frame loss before the observation tick, and zero-byte B1 replies
both at startup and during reads. All Ninja checks passed locally and on the test host.

## Display timing and actual recovery

Frame delivery diagnostics measured 64 complete frames in about 7.304 seconds,
approximately 8.76 fps at V=5. The former viewer assigned 14-fps timestamps.
The current viewer uses actual arrival timestamps, external synchronization,
bounded input buffering, and frame dropping. This addresses the timing mismatch;
it is not a measurement of end-to-end display latency.

The live stream then recorded an interrupted frame with 522240 bytes, emitted
its unavailable/changed-status message, resumed, reset phase tuning, and returned
to complete frames. Another interruption was observed during short-frame retries;
that also resumed. Delivered frame count advanced through 256, 320 and 384 without
manual process restart. A subsequent desktop screenshot showed changed BIOS
contents: CMOS and clock checks passing and a memory-test bar in progress.
Thus observed-status recovery has been exercised on the actual running capture
path. The user's physical reset trigger was not timestamped alongside these log
entries, so this is not a claim that every warm reset is caught.

Remaining limits: a brief signal loss that returns with identical supported timing
before a 100 ms observation can be missed; an already-stalled read with unchanged
valid status may still need manual viewer restart. The tester confirmed that the display now follows the PC promptly. USB disconnect/reconnect and unsupported
modes remain separate qualification work. One ffplay `Invalid maxval: 0` warning
was still seen while frame counts continued; its cause is not yet established.

The user confirmed the repaired viewer follows the PC during reboot.
